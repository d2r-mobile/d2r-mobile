# Redmi K50 Ultra 渲染线程与 GPU 开销，第二轮（2026-10-17）

English: [2026-10-17-perf-round2.md](2026-10-17-perf-round2.md)

接着 [2026-10-17-frame-overlap.zh-CN.md](2026-10-17-frame-overlap.zh-CN.md) 往下做，以那篇的帧重叠（PR #9）为起点。11:30–16:25（新西兰夏令时）在 Redmi K50 Ultra（Adreno 730、Vulkan 1.1、Android 15）上测；从「动态 3D 比例」那一行起，以及发现 12–19，测于 10 月 17 日 23:30 至 18 日 01:40。构建为 `android/linux-build`，引擎改动在分支 `android/perf-round2`。
- **场景：** 同前的营地场景：冷启动，对已存的女巫点「开始」，取最后四个 60 帧的 `NVN PERF v=1` 窗口。
- **标记：** 每一行都开着 `gfx-defer-events=2` 和 `gfx-present-overlap=1`。这两项现在是安卓的缺省（发现 19），不再需要标记文件。
- **温度：** 电池超过约 36 °C 时，就把手机放回桌面晾 30 分钟。下面每组对比都在相近温度下测，每行注明电池温度。
- **工具：** 手机上的 simpleperf（`simpleperf record --app`，cpu-clock，DWARF 调用栈）、引擎自带的逐通道 GPU 计时（`gfx-pass-profile`），以及途中新加的计数（见下）。

**营地：19.7 → 45.7 fps（安卓缺省，动态 3D 比例停在下限 0.6）；比例固定 0.75 时 37 fps。受 GPU 限制。** 到遮挡查询那一行时，3D 选角页已从 24.7–27 fps 升到 39–40 fps。每一步的画面都与默认构建一致（同一场景截图对比）。

管线、写跟踪、复用 Pass 这三行来自同进程 A/B：同一局里每 10 秒开、关一次所测的优化，关的那半分别是 34.1、35.2 和 36.1 fps。

最后一行也是 A/B，3D 比例固定在 0.6，让一帧保持受 CPU 限制。钉核之后一帧又在等 GPU（呈现 3.4 ms）；开着动态比例时，这份余量会变成更高的比例（发现 12）。

## 发现

1. **计时作用域每帧读时钟约 95,000 次。**
   - simpleperf 显示渲染线程 19.3% 在 `__kernel_clock_gettime`，每次约 105 ns。
   - 分项统计（`NVN PERF parts`）改为每 8 帧计一帧。标记 `gfx-perf-sample=N` 可改；设 `1` 恢复每帧都计。
2. **每张彩色图像都带 `VK_IMAGE_CREATE_MUTABLE_FORMAT_BIT` 且不给格式列表，在 Adreno 上会关掉 UBWC。**
   - 去掉后 GPU 少 5.8 ms，CPU 少 3.8 ms（和 CPU 共用的内存流量变少）。
   - 开机、菜单、选角页、营地里，**从来没有一个视图用到别的格式**。Metal 后端为苹果显卡做了同样的选择：按它自己的统计，17,473 张贴图里需要的是 0 张。
   - 现在若遇到格式不同的视图，就像 `nvn_mtl.m` 的 `tex_upgrade_pfv` 那样就地升级：带上这个标志新建图像，逐 level、逐 layer 拷过去，旧图像和视图退役，描述符备忘作废。
   - `gfx-mutable-test=N` 每 N 张图像强制升级一次：营地一局升级 156 次，画面不变。
   - `gfx-mutable-images=1` 恢复原来的做法。
3. **每帧的每个渲染通道都新建再销毁帧缓冲。**
   - 这占渲染线程 5.3%；`vkResetCommandBuffer` 另占 3.6%。
   - 分配器约占 15%：Adreno 驱动在 `vkCmdDraw*` 里 `calloc`，加上引擎每次绘制的 vector 和 map 节点。
   - 现在缓存过的渲染通道的帧缓冲一直保留，直到其中第一张图像被销毁。每个槽有自己的命令池，整池重置。`create_pass` 复用自己的 vector。
4. **每帧 2,188 次绘制里有 558 次每次都重建描述符集**，每次约 21 µs，而备忘命中约 2.5 µs。备忘排除了 uniform 纹素缓冲。
   - 这 558 次绑的都是同一段约 1 MB 的纹素范围，游戏每帧都重写它。
   - 开 `gfx-texel-memo=1` 后每个槽保留一份常驻副本，内容变了才刷新，且只在本帧第一次读之前刷新。副本每次提交校验一次，而不是每次命中都校验；第一版每次命中都算哈希，每帧多花 37 ms。
   - 现在所有绘制都命中备忘，描述符部分从 9.6 ms 降到 5.4 ms。
5. **遮挡查询是 GPU 上最大的单项开销。**
   - 游戏第一次 `ResetCounter` 之后，每次绘制都有自己的精确遮挡查询，每帧约 2,200 个。
   - 一个都不录（诊断用 `gfx-no-occlusion`）时，GPU 从 36.8 ms 降到 26.1 ms，CPU 从 27.4 ms 降到 23.7 ms。
   - 计数仍须正确：在 Metal 上，报告值为 0 时游戏会把篝火和光源剔掉。
   - 仿照 Metal 按渲染通道计数，现在一个查询覆盖一段连续绘制。这段在通道结束、计数清零、报告（报告会结束通道）时结束，所以每次报告仍正好是自清零以来那些绘制的总和。每帧剩 48 个查询。
   - 3D 主通道从 19.1 ms 降到 12.9 ms，界面通道从 3.7 ms 降到 1.3 ms。
   - 在这些场景里，游戏每帧把通过采样数计数器清零 21 次，但这条路径上只报告时间戳（每帧 4 次）。
6. **主通道与分辨率（修遮挡查询之前）。** 把 3D 比例从 0.75 降到 0.6，主通道只从 19.6 ms 降到 16.8 ms。它的开销大部分不随像素数变化；逐次绘制的查询解释了这一点。
7. **存储写跟踪，现在走宿主的缺页钩子：**
   - 每帧拷约 22 KB 而不是 18.7 MB（三块 19.6 MB 缓冲里每帧 6–8 个脏页）；
   - 同进程 A/B（`gfx-ab-toggle` 配 `gfx-ab-target wtrack`：同一局里每 10 秒开、关交替，两半温度相同）：开 36.3 fps、关 35.2 fps，CPU 19.5 ms 对 20.7 ms，无不一致；
   - 在宿主掌管缺页处理时缺省开启（`gfx-no-wtrack` 或 `gfx-wtrack=0` 关掉）；没有这些钩子时仍是可选开启。
8. **管线查找每次绘制都重建可跨启动复用的键**，把布局和渲染通道的定义整段拷进键里，再在以 `std::string` 为键的 map 里查：约占渲染线程 7%。
   - 现在先查一级表：其键只在本进程内有效，用缓存条目指代那两份定义；没命中才建预热列表要用的完整键。
   - A/B：开 35.5 fps、关 34.1 fps，CPU 少 1.0 ms。
9. **每次绘制都完整跑一遍 `create_pass`：** 目标尺寸、帧缓冲规划、附件准备，以及视图、渲染通道、帧缓冲的查找。
   - 现在打开着的通道里、渲染目标状态逐字节相同的绘制直接用上一个 `Pass`。非绘制操作会结束通道，所以其间没有别的东西碰过这些附件；只刷新它们的写入标记。
   - 2,188 次绘制里有 2,140 次走这条路。A/B 中 CPU 从 19.7 ms 降到 17.9 ms，但帧率只从 36.1 到 37.0：一帧现在在等 GPU（呈现 2.7 ms）。
10. **几项小的：**
   - `++stats.draws` 每次绘制做一次顺序一致的原子加（占线程 2.7%，因为要等之前所有写入完成）；它只是诊断计数，改为宽松原子。
   - 每次提交的快照 map 复用节点。
   - 回读放进缓存内存（`gfx-readback-cached`）没有可测的差别：这台机器上它选到的是同一种内存类型（发现 14）。
   - 时间戳报告改为就地写入，不再结束通道并加两道完整屏障；A/B 中 GPU 没有差别（被它拆开的都是小通道）。
11. **做完以上之后的 3D 比例（手动固定比例）：** 用 0.6 代替 0.75 时，GPU 时间是 21.4 ms 而不是 25.3 ms，营地 39.5 fps。主通道从 12.9 ms 降到 10.6 ms，可见它仍有约一半不随像素数变化，多半是每次绘制的状态在每个分块里重放。比例是画质取舍，保持 0.75。

12. **动态 3D 比例现在在安卓上生效。**
   - `hle_oe.c` 里的控制器（`dm_3d_scale_feed`，规则同 iOS）要知道每帧上屏的时刻。现在由 Vulkan 桥报出（`nvn_vk.c` 的 `mtl_presented_time`）。
   - 进游戏先停判 20 秒；之后只要有帧超过 25 ms，比例就按 0.75 → 0.70 → 0.65 → 0.60（下限）逐级降，连续 30 秒不掉帧再升回一级。
   - 停在下限时营地 38.8–40.5 fps。玩家选「画质优先」（`q3d=1`）时保持 0.75。测量时用 env 文件固定比例：`DM_3D_SCALE=0.6`、`DM_3D_SCALE_DYN=0`。
13. **游戏线程从不在 X2 核上跑。**
   - 电池 30 °C 时 MIUI 就给各核封了顶：A510 2.02 GHz 封到 1.80，A710 2.75 封到 2.57，X2 3.19 封到 2.25。
   - 调度器一直把游戏线程（同步翻译时它也做翻译）放在 A710 上（cpu4–6），X2（cpu7）空闲在 0.79 GHz。MIUI 还会在运行中改写这个线程的可用核掩码（先 0-5,7，再 0-4,6-7，再 0-7）。
   - 从 App 外面用 `taskset` 被拒（SELinux，`run-as` 也一样），所以现在由呈现端把调用呈现的线程钉到 `cpuinfo_max_freq` 最高的核上，每 120 次呈现核对一次掩码。
   - 启动时安卓会短暂把 App 放进不含 cpu7 的 cpuset，这时重钉被拒。内核会记住这个请求，等 cpuset 允许时再生效，下一次核对也会重试。
   - 比例 0.6 下 A/B：40.2 → 44.3 fps，CPU 17.1 → 14.3 ms。即使封顶在 2.25 GHz，X2 也比 2.57 GHz 的 A710 快。
   - 更温和的 ADPF（`APerformanceHint`）在这版 MIUI 上拿不到会话。
14. **流式内存读起来像不带缓存的内存。**
   - 这里缓冲只能用内存类型 0 和 6。类型 6 标着主机可见、一致、带缓存，所以流式区和回读区都在它里面。
   - `gfx-membench` 测得类型 6 的 CPU 写是 9.4 GB/s，CPU 读却只有 1.1 GB/s，不管数据是 GPU 写的还是 CPU 写的。
   - 所以存储写回（每帧 1.3 MB）要 1.06 ms。
   - 写跟踪的安全核对每 240 次使用就把整块 19.6 MB 的跟踪缓冲与客体内存比一遍：按这个速度在一帧里约 18 ms。现在每次使用比 16 页（至今从未记到不一致）。
   - `readback_buffer` 不再先把随后整个拷过去的字节清零。
15. **顶点与索引拷贝几乎每帧都不变**（诊断 `gfx-snap-census`，分支 `android/snap-census`）。

    | 种类 | 每帧区间数 | 每帧 MB | 与上一帧相同 |
    |---|---|---|---|
    | 顶点 | 1,138 | 6.42 | 6.34 MB（99%） |
    | 索引 | 439 | 1.45 | 1.45 MB（100%） |
    | uniform | 1,778 | 1.77 | 0 |

    **现在跨帧缓存**（`gfx-vcache`，PR #11，安卓缺省开）。一段区间只拷一次进常驻区，只要 HLE 的写保护脏页跟踪（`nvn_dirty.c`，Metal 后端给贴图用的那套）报告拷贝之后它的页没被写过，就一直复用。
    - 比例 0.6、不钉核时 A/B：CPU 17.24 → 16.52 ms，39.95 → 40.79 fps。
    - 每帧 658 段（7.8 MB）来自缓存，两半的画面一致。
    - 拷进来 8 次提交内又变的区间退回每帧拷贝。页从不与存储写跟踪共用，否则各自会吞掉对方的缺页。
16. **快照前置缓存。** 命令流里每次 CPU 写客体内存（每帧约 30 次）都会清空整个 4,096 槽的前置缓存，而这些写没有一次与快照重叠。现在失效只清掉被删条目的那几个槽。由 map 而不是前置缓存答复的查找从每帧 714 次降到 245 次；CPU 少 0.12 ms（A/B 目标 `snapinval`）。
17. **异步翻译在这里更慢：20.0–22.6 fps，对比 37.5**（`DM_NVN_SYNC=0`，即 iOS 用的 HLE 翻译队列）。
   - 这时游戏每帧在它自己的同步等待里等 17.9–23.8 ms（`NVN PERF block_ms` 的 `legacy_wait`；同步模式下为 0）。
   - 这些等待每帧额外逼出 0.4 次提交。它等的栅栏属于翻译线程还没做完的工作，或还在未提交的槽里（每帧在呈现时提交一次）。
   - GPU 时间也升到 28–34 ms。安卓仍缺省用同步模式。
18. **营地 10 分钟浸泡（比例固定 0.75，在钉核之前）：** 第 1 分钟 37.5 fps（26.0 °C），第 5 分钟 36.9（31.0 °C），第 10 分钟 37.0（34.7 °C）。CPU 封顶一直是 2.57 / 2.25 GHz。
19. **帧重叠现在是安卓的缺省。** 没有 `gfx-defer-events=2` 和 `gfx-present-overlap=1` 时，新装的 App 在营地只有 7.7 fps。
   - 没有标记时引擎读 `DM_GFX_DEFER_EVENTS`，安卓 App 把它设成 2，其他宿主保持原来的缺省。
   - 呈现端缺省重叠呈现，标记写 `0` 时才关。
20. **BC 贴图上传时都被解码，尽管 GPU 能采样 BC。** 每张 BC1–7 贴图都经 bcdec 解成 RGBA8、R16、RG16 或 RGBA16F，这条路是为不支持 BC 的 GPU 准备的。Adreno 730 能采样全部 BC 格式，所以现在这些贴图保持原格式（`gfx-native-bc`，PR #12，安卓缺省开）。
    - 比例 0.6、钉核时 GPU 21.35 → 20.85 ms（3D 主通道 10,420 → 10,055 µs），44.5 → 45.7 fps。
    - 图像内存 827 → 320 MB：同样 161 MB 的数据，BC 图像从 693 MB 降到 186 MB。
    - 这台机器上 `dumpsys meminfo` 的「Graphics」反映不出这部分只在 GPU 上的内存；上面的数是驱动给的分配大小，由 `NVN PERF textures` 统计。
    - 截图一致。
21. **试过、没有收益的：**
    - **游戏的屏障。** 每帧 66 次 `nvnCommandBufferBarrier` 中，48 次结束了打开着的通道，其中 34 次又以相同渲染目标重开通道。位全是排序、贴图失效或 zcull（`0x12` 32 次，以及 `0x10`、`0x11`、`0x13` 等）。
      - 让通道跨过它们保持打开、把冒险交给引擎自己的跟踪（`prepare_read`），只是挪动了拆分点：每帧通道数从 54 变成 64，GPU 时间不变。
      - 这类屏障之后的绘制会采样本通道刚画的东西，是真实的写后读依赖。此改动没有保留。
    - **呈现前清屏。** 呈现端在 blit 之前把整幅 2712×1220 交换链图像清黑，而 blit 只差一列就铺满。跳过它没有差别（A/B 45.76 对 45.78 fps），多半是压缩图像上的快速清除。
    - **流式区的内存类型：** 见发现 14，缓冲只能用类型 6。
22. **屏幕跑在 60 Hz**（`dumpsys SurfaceFlinger`：`vsyncRate=60.00 Hz`；面板支持 120）。约 45 fps 时，FIFO 交换链按 16.7 ms 和 33.3 ms 交替的间隔上屏。请求 120 Hz（`ANativeWindow_setFrameRate`）也许能让节奏更匀，但它和 HLE 按 60 Hz 节拍的出图节奏相互影响。还没试。

## 现在一帧的时间去向

- **钉核后，在 0.6 下限上一帧受 GPU 限制：** 用原格式 BC 时 GPU 20.85 ms（3D 主通道 10.06 ms），CPU 提交 13.5 ms，呈现 3.4 ms（大部分在等 GPU）。开着动态比例时，比例会一直升到 GPU 约 25 ms 为止。
- **比例 0.6 下各通道的 GPU 时间：**

  | 通道 | 尺寸 | 绘制数 | µs |
  |---|---|---|---|
  | 3D 主通道（颜色 + 深度） | 1200×540 | 542 | 10,590 |
  | 阴影图 | 1024×1024 | 86 | 2,071 |
  | 深度预通道 | 1200×540 | 542 | 1,787 |
  | UI | 2000×900 | 837 | 1,314 |
  | 计算（32×20 组，在预通道之后） | — | — | 854 |
  | 特效 | 1200×540 | 15 | 672 |
  | 第二张阴影图 | 1024×1024 | 119 | 390 |
  | 最后两个通道 | 2000×900 | 2 | 527 |
  | 约 50 个小通道（模糊链之类） | — | — | 约 3,200 |

  一帧的时间跨度（21.6 ms）里 GPU 有 99% 在忙。
- **渲染线程上 CPU 最大的几项（simpleperf）：** `memcpy` 13.8%（快照拷贝 6.6%、写回 4.3%），描述符自身 7.4%，驱动的 `vkCmdBindDescriptorSets` 5.8% 和 `vkCmdDrawIndexed` 3.6%，命令循环 3.4%，绘制准备 3.4%。
