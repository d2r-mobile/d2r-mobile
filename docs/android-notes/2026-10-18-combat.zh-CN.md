# Redmi K50 Ultra 上的战斗：黑方块与片元着色器的四元组洗牌（2026-10-18）

English: [2026-10-18-combat.md](2026-10-18-combat.md)

08:44–10:06（新西兰夏令时）在 Redmi K50 Ultra（Adreno 730、Vulkan 1.1、Android 15）上测。构建为 `android/linux-build`，用的是[第二轮](2026-10-17-perf-round2.zh-CN.md)的安卓缺省。修复是 PR #13（分支 `android/quad-derivatives`）。

## 不用手玩也能进战斗

存档的女巫只开了营地的传送点。宿主自带的测试开关写进 `files/dm/env`，几秒钟就能把她送进战斗：

| 行 | 作用 |
|---|---|
| `DM_TEST_WARP_LV=250:8` | 游戏第 250 拍（10 秒）把玩家送进 8 号关卡，即邪恶洞穴（游戏自己的换图，同走传送门） |
| `DM_TEST_WORLD_SEEK=380:1:c19:L8` | 从第 380 拍起，在 8 号关卡里一间房一间房地跳，找到类号 19（沉沦魔）的单位后走过去 |
| `DM_TEST_WORLD_LIST=450` | 列出已载入的怪物与物件，带类号和格坐标 |
| `DM_GAME_SEED=12345` | 游戏自带的固定种子：每次关卡布局与怪群都一样，可以做前后对比 |

打斗本身是脚本按「攻击」，每 15 秒喝一瓶药（草稿目录里的 `combat.sh`；电池超过 36 °C 时它不会开始）。1 级女巫对一群沉沦魔和沉沦魔巫师，通常一分钟内就会死。对测试角色来说这没关系。

## 单位周围的黑方块

第一次打斗时，玩家、怪物、尸体和掉落物周围的地面被一块块黑方块盖住。方块里单位和物品标签照样画出来，黑色里还夹着白色噪点。打斗之前的洞穴和营地都正常。

**排除掉的：**
- **不是安卓这边的改动。** 把较新的引擎选项都用标记关掉（帧重叠、`MUTABLE_FORMAT`、持久帧缓冲、每槽命令池、纹素备忘、按段遮挡查询、写跟踪、就地时间戳、原格式 BC、顶点缓存：也就是原来约 12 fps 的老路径），黑方块还在。把描述符与绑定缓存全关（`gfx-no-descmemo`、`-xmemo`、`-bindcache`、`-imgcache`、`-dynpartial`）也还在。
- **不是 NaN 经过 min / max。** 着色器库用的是 `FMin`/`FMax`/`FClamp`（共约 17.9 万处，从不用 NaN 安全的 `NMin`/`NMax`/`NClamp`）；改成 NaN 安全的写法后没有变化。

**原因：**
- 把片元着色器里的 `OpGroupNonUniformShuffle` 换成本 lane 自己的值，黑方块就没了。
- 182 个片元着色器各含一处这样的洗牌：Maxwell 的 `SHFL.BFLY` 四元组换位译过来的 `gl_SubgroupInvocationID ^ 2`，即同一 2×2 四元组里竖直方向的邻居像素。在主通道着色器里，它位于点光源那一支，挨着 `dFdx`/`dFdy`。
- Vulkan 不保证辅助调用（三角形外、只为求导而存在的像素）参与子组操作。Adreno 上它们取到的是垃圾值，由此产生的 NaN 再经模糊链扩散开来。
- 单位的三角形边缘多，洞穴里又有火把和火焰照着它们，所以黑方块总跟着单位。

**修复**（`dm/gfx/vulkan/engine/xbg_spirv_quad.cpp`）：片元模块里每一处浮点洗牌，现在都改由精细导数求四元组邻居；求导一定有辅助调用参与。
- 同一四元组里 `dFdxFine(v)` = 右 − 左，所以左像素的邻居是 `v + d`，右像素的是 `v − d`；竖直方向同理。
- 像素在四元组里的位置由 `gl_FragCoord` 的奇偶得出。
- 182 个着色器全部改写，并通过 `spirv-val --target-env vulkan1.1`。
- 安卓上缺省开启（`DM_GFX_QUAD_DERIVATIVES`）；标记 `gfx-quad-derivatives` 写 0 时关掉。
- 后来发现：这些洗牌都在翻译器的 `ShuffleXor` 辅助函数里，它的 clamp 检查还会让 64 道子组的 32–63 号 lane 拿回自己的值。`main` 带守卫的版本在 PR #27 里改到调用处；见 [2026-10-19-spin-events-quad.zh-CN.md](2026-10-19-spin-events-quad.zh-CN.md)。

## 这个修复也是至今最大的 GPU 收益

同一个 APK 先后两次冷启动，只切换 `gfx-quad-derivatives`：

| 场景 | 修复关 | 修复开 |
|---|---|---|
| 营地，3D 比例固定 0.6，钉 X2 | 44.7–44.9 fps，GPU 21.3 ms | **50.2–50.9 fps，GPU 17.6 ms** |
| 邪恶洞穴打斗，`DM_GAME_SEED=12345`，前 12 秒，比例 0.75 | 38.8–41.0 fps，GPU 23.3–24.3 ms | **50.7–52.2 fps，GPU 18.0–18.5 ms** |

**怎么看这些数：**
- 两次打斗的绘制数差约 8%（1,100–1,137 对 963–1,070），因为战斗不会完全重演；营地是同一个场景。
- 片元着色器里的一次子组洗牌，在 Adreno 上的代价显然远不止一条指令。
- **开着安卓缺省（动态 3D 比例）时：** 营地现在在 0.75 上停留约 90 秒，之后稳定在 0.65，47–50 fps。修复之前它停在下限 0.6，约 45.5 fps。
- 比例 0.6 下营地又受 CPU 限制：提交 13.7 ms，GPU 17.6 ms。

## 打斗中还看到的

- **修复之前，洞穴打斗受 GPU 限制：** 比例 0.75 时 36–37 fps（GPU 25.8 ms），0.70 时 42 fps（GPU 22.7 ms），约 1,100 次绘制。比例 0.70 下各通道：

  | 通道 | 绘制数 | µs |
  |---|---|---|
  | 3D 主通道 | 312 | 10,614（每次绘制 34 µs，营地为 19：点光源多） |
  | 阴影图 | 204 | 2,852 |
  | 深度预通道 | 312 | 2,266 |
  | 特效 | 45 | 1,234 |
  | 光源剔除计算（32×20 分块） | — | 860 |

- **第一次见到新内容时的卡顿：** 第一群怪进入视野时出现 683 ms 和 291 ms 的长帧，几乎全花在提交上（驱动建管线）。之后的各次都没再出现，因为引擎的预热列表会在启动时重建记下的管线。改写过的着色器会在这次预热里重编一次（首帧 1.5 秒，原来 0.8 秒）。
- **顶点 / 索引缓存的写保护缺页：** 载入和菜单期间每秒约 160 次，打斗中每秒 2–25 次。洞穴里缓存每帧供应 224–251 段（2.3–4.1 MB）。
- **打斗中的 CPU：** 提交 9–12 ms；剖析结果与营地类似（`memcpy` 12%，描述符 5%）。
