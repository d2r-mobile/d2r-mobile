## 时间花在哪

**旧计数漏了什么。** `NVN PERF waits` 把每次槽退役都算上，连栅栏早已发信号的也算，看不出 CPU 卡在哪。

**新计数。** source snapshot` 新增 `NVN PERF block_ms` 一行，只计栅栏仍忙时的等待，并按调用处分开：
- 槽环回绕、呈现、事件、arena、`gpu_sync`、`complete_all`、轮询、游戏同步等待；

同时记下每次提交由哪一处触发。

营地里看到的：
- **游戏自己从不等它的同步对象：** `legacy_wait_total=0`。也从不读还没发布的事件：`cpu_reads_pending=0`。所有阻塞都是后端在等自己。
- **默认：** 每帧两次命令缓冲 SignalEvent 各调一次 `complete_all()`，CPU 每帧两次等 GPU 做完全部工作。
- **`gfx-defer-events`=1**（到信号处提交、退役时发布）去掉了这两次等待。但一帧变成 3 次提交，2 槽环在帧内回绕，回绕时要等第一次提交做完：约 57 ms。
- **呈现层每次呈现后都等 blit 栅栏，再 `vkQueueWaitIdle`。** 即使帧内不再等，第 N+1 帧也要等第 N 帧的 GPU 工作全部做完才能开始翻译。E2 就是这样：呈现要 62 ms。

## 改动（分支 试验构建，可选开启）

- **`gfx-defer-events` = `2`：** SignalEvent 不提交。
  - 值挂在正在录制的槽上，等这个槽退役时、在它的回写之后再发布。
  - 营地一帧始终只有一次提交，槽环不会在帧内回绕。
  - 对未发布事件调 `nvnEventGetValue` 仍会先强制完成（`xbg_game_event_read`），并计数。
- **`gfx-present-overlap` = `1`：** 呈现层最多两次 blit 在途。
  - 每份在途帧有自己的命令池、获取信号量和栅栏。只等即将复用的那一份的栅栏，不再等栅栏加整个队列。
  - 呈现失败时，仍和原来一样先排空队列再拆交换链。
  - **为什么源图安全：** 引擎之后对被呈现图像的屏障都是 `ALL_COMMANDS → ALL_COMMANDS`。释放的图像要等更晚的槽退役才销毁，该栅栏按队列顺序覆盖这次 blit。

## 延后发布暴露出的泄漏

`resolve_known_reports()` 只在没有任何计数报告待处理时，才清掉旧的遮挡计数 epoch。
- **为什么一直清不到：** 事件延后发布后，总有报告在途（营地里 8 个），旧 epoch 一直没被清掉。D2R 每帧重置计数约 13 次，2.5 分钟后表里有 30,462 个 epoch。
- **代价：** 每次槽退役都要遍历这张表，清理时间每分钟每帧多约 1 ms。
- **为什么默认构建看不出来：** 每次事件的 `complete_all()` 会把一切都清掉。
- **修复（source snapshot`）：** 清掉所有没有待处理报告引用的旧 epoch。报告只会引用它录制时的当前 epoch，而槽退役时本来就会跳过指向已清除 epoch 的查询引用。

## 温度

连跑约一小时后，电池 38.5 °C。CPU 上限降到：
- cpu4–6：2.00 GHz，原为 2.57；
- cpu7：1.88 GHz，原为 3.19。

两项都开时主线程占约 97% 的一个核。17 fps 与 22 fps 的窗口之间，一帧各部分都同样差约 25%，可见那次长跑中的起伏来自 CPU 速度。现在持续帧率取决于每帧 CPU 工作量和手机温度。
