# Render thread and GPU costs on the Redmi K50 Ultra, round 2 (2026-10-17)

中文：[2026-10-17-perf-round2.zh-CN.md](2026-10-17-perf-round2.zh-CN.md)

This picks up after [2026-10-17-frame-overlap.md](2026-10-17-frame-overlap.md); that note's frame overlap (PR #9) is the starting point. Measured 11:30–16:25 NZDT on the Redmi K50 Ultra (Adreno 730, Vulkan 1.1, Android 15); the rows from the dynamic 3D scale on, and findings 12–19, from 17 Oct 23:30 to 18 Oct 01:40. Build `android/linux-build`; engine changes on branch `android/perf-round2`.
- **Scene:** the same camp scene as before: cold start, Play on the saved Sorceress, last four 60-frame `NVN PERF v=1` windows.
- **Markers:** `gfx-defer-events=2` and `gfx-present-overlap=1` are on in every row. Both are now the Android default (finding 19), so the marker files are no longer needed.
- **Temperature:** the phone was left on the home screen for 30 minutes whenever the battery passed about 36 °C. Every comparison below is between runs at similar temperature; the battery temperature is noted per row.
- **Tools:** simpleperf on the device (`simpleperf record --app`, cpu-clock, DWARF call graphs), the engine's per-pass GPU timer (`gfx-pass-profile`), and the counters added on the way (below).

**Camp: 19.7 → 45.7 fps with the Android defaults (the dynamic 3D scale settles on its 0.6 floor); 37 fps with the scale held at 0.75. GPU bound.** The 3D character select went from 24.7–27 to 39–40 fps by the occlusion-query row. The picture stayed the same as the default build in every step (screenshots compared in the same scene).

The pipeline, write-tracking and pass-reuse rows come from in-process A/B runs. Each optimization was switched on and off every 10 s within one run, and the off phases gave 34.1, 35.2 and 36.1 fps.

The last row is also an A/B, with the 3D scale held at 0.6 so that the frame stays CPU bound. With the pin the frame waits for the GPU again (present 3.4 ms). With the dynamic scale on, that headroom goes to a higher scale (finding 12).

## Findings

1. **The timing scopes read the clock about 95,000 times per frame.**
   - simpleperf put 19.3% of the render thread in `__kernel_clock_gettime`, at about 105 ns per read.
   - The per-part breakdown (`NVN PERF parts`) now runs on one frame in 8. Marker `gfx-perf-sample=N` changes that; `1` restores every frame.
2. **`VK_IMAGE_CREATE_MUTABLE_FORMAT_BIT` on every color image, with no format list, turns off UBWC on Adreno.**
   - Dropping it cut GPU time by 5.8 ms and CPU time by 3.8 ms (less memory traffic shared with the CPU).
   - **No view ever used a different format** across boot, menus, character select and the camp. The Metal backend made the same choice for Apple GPUs: in its own counts, 0 of 17,473 textures needed one.
   - A differing view now upgrades the image in place, as `tex_upgrade_pfv` does in `nvn_mtl.m`: a new image with the flag, a copy of every level and layer, the old image and views retired, and the descriptor memo dropped.
   - `gfx-mutable-test=N` forces the upgrade on every Nth image: 156 upgrades in a camp run, picture unchanged.
   - `gfx-mutable-images=1` restores the old behaviour.
3. **Framebuffers were created and destroyed for every pass of every frame.**
   - That was 5.3% of the render thread; `vkResetCommandBuffer` took another 3.6%.
   - The allocator took about 15%: the Adreno driver `calloc`s inside `vkCmdDraw*`, plus the engine's per-draw vectors and map nodes.
   - Framebuffers of cached render passes now live until the first of their images is destroyed. Each slot has its own command pool, reset whole. `create_pass` reuses its vectors.
4. **558 of 2,188 draws per frame rebuilt their descriptor set every time**, about 21 µs each against about 2.5 µs for a memo hit. The memo excluded uniform texel buffers.
   - All 558 bind one texel range of about 1 MB, which the game rewrites every frame.
   - With `gfx-texel-memo=1` each slot keeps a resident copy, refreshed when its content changes, before its first read in a frame. It is verified once per submission instead of on every hit; hashing it per hit cost 37 ms per frame on the first try.
   - Every draw now hits the memo; the descriptor part fell from 9.6 to 5.4 ms.
5. **Occlusion queries were the largest single GPU cost.**
   - After the game's first `ResetCounter`, every draw got its own precise occlusion query, about 2,200 per frame.
   - Recording none (diagnostic `gfx-no-occlusion`) took GPU time from 36.8 to 26.1 ms and CPU from 27.4 to 23.7 ms.
   - The counters still have to be right: on Metal, reports of 0 made the game cull campfires and lights.
   - As Metal counts per render pass, a query now covers a run of draws. The run ends with the pass, at a counter reset, and at a report (which ends the pass), so a report still sums exactly the draws since its reset. That leaves 48 queries per frame.
   - The main 3D pass went from 19.1 to 12.9 ms, and the UI pass from 3.7 to 1.3 ms.
   - In these scenes the game resets the samples counter 21 times per frame and reports only timestamps (4 per frame) on this path.
6. **Main pass and resolution (before the occlusion fix).** Lowering the 3D scale from 0.75 to 0.6 took the main pass only from 19.6 to 16.8 ms. Most of its cost did not scale with pixels; the per-draw queries explain that.
7. **Storage write tracking, now through the host's fault hooks:**
   - it copies about 22 KB per frame instead of 18.7 MB (6–8 dirty pages of three 19.6 MB buffers);
   - an in-process A/B (`gfx-ab-toggle` with `gfx-ab-target wtrack`: on and off alternate every 10 s in one run, so both see the same temperature) measured 36.3 fps on against 35.2 off, CPU 19.5 against 20.7 ms, with no mismatches;
   - it is on by default where the host owns the fault handler (`gfx-no-wtrack` or `gfx-wtrack=0` turn it off); without the hooks it stays opt-in.
8. **Pipeline lookup rebuilt the launch-stable key on every draw**, copying the layout and render-pass definitions into it, then searched a `std::string`-keyed map: about 7% of the render thread.
   - A first-level map now uses a process-local key that names those definitions by their cached entries; only a miss builds the full key that the warm-up list needs.
   - A/B: 35.5 fps on against 34.1 off, CPU −1.0 ms.
9. **`create_pass` ran in full for every draw:** target extents, framebuffer plan, attachment preparation, and view, render-pass and framebuffer lookups.
   - A draw in the open pass with byte-identical render-target state now gets the previous `Pass`. Non-draw ops end the pass, so nothing else touched its attachments; only their write marks are refreshed.
   - 2,140 of 2,188 draws take it. CPU fell from 19.7 to 17.9 ms in the A/B, but fps only from 36.1 to 37.0: the frame now waits for the GPU (present 2.7 ms).
10. **Smaller ones:**
   - `++stats.draws` was a sequentially consistent atomic add per draw (2.7% of the thread, since it waits for every earlier store); it is a diagnostic counter, now relaxed.
   - The per-submission snapshot maps now recycle their nodes.
   - Cached readback memory (`gfx-readback-cached`) made no measurable difference: on this device it picks the same memory type (finding 14).
   - Timestamp reports are now written in place instead of ending the pass with two full barriers; the A/B showed no GPU difference (the passes they split were small).
11. **3D scale, after all the above (scale fixed by hand):** at 0.6 instead of 0.75, GPU time is 21.4 ms instead of 25.3 and the camp runs at 39.5 fps. The main pass drops from 12.9 to 10.6 ms, so about half of it still does not scale with pixels; most likely per-draw state replayed in each tile bin. The scale is a quality choice and is left at 0.75.

12. **The dynamic 3D scale now works on Android.**
   - The controller in `hle_oe.c` (`dm_3d_scale_feed`, the same rules as iOS) needs the time each frame was presented. The Vulkan bridge now reports it (`mtl_presented_time` in `nvn_vk.c`).
   - After a 20 s hold on entering the game, the scale steps 0.75 → 0.70 → 0.65 → 0.60 (the floor) while frames take longer than 25 ms, and steps back up after 30 s without one.
   - At the floor the camp ran at 38.8–40.5 fps. The player's "quality first" setting (`q3d=1`) keeps 0.75. For measurements, the env file holds the scale: `DM_3D_SCALE=0.6`, `DM_3D_SCALE_DYN=0`.
13. **The game thread never ran on the X2 core.**
   - With the battery at 30 °C, MIUI caps the cores: A510 1.80 of 2.02 GHz, A710 2.57 of 2.75, X2 2.25 of 3.19.
   - The scheduler kept the game thread (which also translates in sync mode) on the A710 cores (cpu4–6). The X2 (cpu7) sat at 0.79 GHz. MIUI also rewrote the thread's allowed-CPU mask while it ran (0-5,7, then 0-4,6-7, then 0-7).
   - `taskset` from outside the app is refused (SELinux, `run-as` included), so the presenter now pins the thread that calls present to the cores with the highest `cpuinfo_max_freq`, and checks the mask every 120 presents.
   - At start Android briefly has the app in a cpuset without cpu7, and the re-pin is refused. The kernel keeps the request and applies it once the cpuset allows, and the next check retries.
   - A/B with the scale at 0.6: 40.2 → 44.3 fps, CPU 17.1 → 14.3 ms. Even capped at 2.25 GHz, the X2 is faster than an A710 at 2.57.
   - ADPF (`APerformanceHint`, the gentler route) returns no session on this MIUI build.
14. **Arena memory reads like uncached memory.**
   - Buffers may only use memory types 0 and 6 here. Type 6 is host visible, coherent and cached, so the stream and readback arenas are all in it.
   - `gfx-membench` measured type 6 at 9.4 GB/s for CPU writes, but only 1.1 GB/s for CPU reads, whether the GPU or the CPU wrote the data.
   - Storage writebacks (1.3 MB per frame) therefore take 1.06 ms.
   - The write-tracking safety check compared a whole 19.6 MB tracked buffer with guest memory every 240 uses: about 18 ms in one frame at that speed. It now compares 16 pages per use (no mismatch has ever been logged).
   - `readback_buffer` no longer zeroes the bytes it then copies over.
15. **Vertex and index copies are almost all unchanged from frame to frame** (diagnostic `gfx-snap-census`, branch `android/snap-census`).

    | Kind | Ranges per frame | MB per frame | Same as the previous frame |
    |---|---|---|---|
    | Vertex | 1,138 | 6.42 | 6.34 MB (99%) |
    | Index | 439 | 1.45 | 1.45 MB (100%) |
    | Uniform | 1,778 | 1.77 | 0 |

    **Now cached across frames** (`gfx-vcache`, PR #11, on by default on Android). A range is copied once into a persistent arena and reused while the HLE's write-protect dirty-page tracker (`nvn_dirty.c`, which the Metal backend uses for textures) reports no write to its pages since the copy.
    - A/B at scale 0.6 with the pin off: CPU 17.24 → 16.52 ms, 39.95 → 40.79 fps.
    - 658 ranges (7.8 MB) per frame come from the cache, and the picture matched between the phases.
    - Ranges that change again within 8 submissions go back to per-frame copies. Pages are never shared with the storage write tracker, since each would take the other's faults.
16. **Snapshot front cache.** Each in-stream CPU write to guest memory (about 30 per frame) emptied the whole 4,096-slot front cache, and none of those writes overlapped a snapshot. The invalidation now clears only the slots of the entries it erases. Lookups answered by the map instead of the front fell from 714 to 245 per frame; CPU −0.12 ms (A/B target `snapinval`).
17. **Asynchronous translation is slower here: 20.0–22.6 fps against 37.5** (`DM_NVN_SYNC=0`, the HLE translation queue used on iOS).
   - The game then waits 17.9–23.8 ms per frame in its own sync waits (`legacy_wait` in `NVN PERF block_ms`; 0 in sync mode).
   - Those waits force 0.4 extra submissions per frame. The fences belong to work that the translation thread hasn't finished, or that still sits in the unsubmitted slot (one submission per frame, at present).
   - GPU time also rose to 28–34 ms. Sync mode stays the Android default.
18. **10-minute camp soak (scale fixed at 0.75, before the pin):** 37.5 fps at minute 1 (26.0 °C), 36.9 at minute 5 (31.0 °C), 37.0 at minute 10 (34.7 °C). The CPU caps stayed at 2.57 / 2.25 GHz.
19. **Frame overlap is the Android default now.** Without `gfx-defer-events=2` and `gfx-present-overlap=1` a fresh install ran the camp at 7.7 fps.
   - The engine reads `DM_GFX_DEFER_EVENTS` when there is no marker, and the Android app sets it to 2, so other hosts keep their default.
   - The presenter overlaps presents unless the marker holds `0`.
20. **BC textures were decoded on upload, although the GPU samples BC.** Every BC1–7 texture went through bcdec to RGBA8, R16, RG16 or RGBA16F, a path for GPUs without BC. The Adreno 730 samples all BC formats, so these textures now keep their own format (`gfx-native-bc`, PR #12, on by default on Android).
    - GPU 21.35 → 20.85 ms (main 3D pass 10,420 → 10,055 µs), 44.5 → 45.7 fps at scale 0.6 with the pin.
    - Live image memory 827 → 320 MB: the BC images take 186 MB instead of 693 MB, for the same 161 MB payload.
    - `dumpsys meminfo` "Graphics" does not follow this GPU-only memory on this device; the numbers are the driver's allocation sizes, counted in `NVN PERF textures`.
    - Screenshots match.
21. **Tried, no gain:**
    - **Game barriers.** Of the 66 `nvnCommandBufferBarrier` calls per frame, 48 end an open pass and 34 of those reopen the same render targets. All the bits are ordering, texture-invalidate or zcull (`0x12` 32 times, `0x10`, `0x11`, `0x13` and others).
      - Keeping the pass open across them, and leaving hazards to the engine's own tracking (`prepare_read`), moved the splits rather than removing them: passes per frame went from 54 to 64, with no GPU change.
      - The draw after such a barrier samples what the pass just rendered, so these are real read-after-write dependencies. The change was not kept.
    - **Present clear.** The presenter clears the whole 2712×1220 swapchain image before a blit that covers all but one column. Skipping it made no difference (A/B 45.76 vs 45.78 fps), presumably a fast clear on a compressed image.
    - **Arena memory types:** see finding 14. Only type 6 is available for buffers.
22. **The display runs at 60 Hz** (`dumpsys SurfaceFlinger`: `vsyncRate=60.00 Hz`; the panel does 120). At about 45 fps a FIFO swapchain shows frames at a mix of 16.7 and 33.3 ms intervals. A 120 Hz request (`ANativeWindow_setFrameRate`) might smooth that, but it interacts with the HLE's present pacing, which beats at 60 Hz. Not tried yet.

## Where the frame goes now

- **With the pin, the frame is GPU bound at the 0.6 floor:** GPU 20.85 ms with native BC (main 3D pass 10.06 ms), CPU submit 13.5 ms, present 3.4 ms (mostly waiting for the GPU). With the dynamic scale on, the scale rises until the GPU takes about 25 ms.
- **GPU per pass at scale 0.6:**

  | Pass | Size | Draws | µs |
  |---|---|---|---|
  | Main 3D (color + depth) | 1200×540 | 542 | 10,590 |
  | Shadow map | 1024×1024 | 86 | 2,071 |
  | Depth pre-pass | 1200×540 | 542 | 1,787 |
  | UI | 2000×900 | 837 | 1,314 |
  | Compute (32×20 groups, after the pre-pass) | — | — | 854 |
  | Effects | 1200×540 | 15 | 672 |
  | Second shadow map | 1024×1024 | 119 | 390 |
  | Final passes (2) | 2000×900 | 2 | 527 |
  | About 50 small passes (blur chains and the like) | — | — | about 3,200 |

  The GPU is busy for 99% of the frame span (21.6 ms).
- **Biggest CPU items on the render thread (simpleperf):** `memcpy` 13.8% (snapshot copies 6.6%, writebacks 4.3%), descriptors 7.4% self, driver `vkCmdBindDescriptorSets` 5.8% and `vkCmdDrawIndexed` 3.6%, the command loop 3.4%, draw setup 3.4%.

|---|---|---|
| `gfx-perf-sample` = N | per-part timing on 1 frame in 32 | 1 frame in N; 0 = off |
| `gfx-mutable-images` = 1 | color images without `MUTABLE_FORMAT` | every color image mutable, as before |
| `gfx-mutable-test` = N | — | test: force the in-place upgrade on every Nth color image |
| `gfx-no-persistent-fb` | framebuffers kept across frames | per-slot framebuffers, as before |

| `gfx-no-texel-memo` | resident texel copies, memoized sets | per-frame texel views, as before |

| `gfx-no-occlusion` = 1 | — | diagnostic: no occlusion queries; reports read 0 |
| `gfx-no-wtrack` (or `gfx-wtrack` = 0) | write tracking on where the host owns the fault handler | off |
| `gfx-readback-cached` = 1 | readback arena in a coherent memory type | prefer a cached type (the same type 6 on Adreno 730, so no effect) |
| `gfx-heavy-timestamps` = 1 | timestamp reports written in place | end the pass with full barriers, as before |
| `gfx-ab-toggle` = N with `gfx-ab-target` | — | in-process A/B: the target (`wtrack`, `pipefast`, `query`, `timestamps`, `passfast`, `snapinval` or `pin`) is off every other N seconds |

| `gfx-defer-events` = 0 / 1 / 2 | 2 on Android (`DM_GFX_DEFER_EVENTS`), 0 elsewhere | that mode |
| `gfx-present-overlap` = 0 | two presents in flight | drain after every present, as before |
