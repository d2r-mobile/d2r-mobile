# Redmi K50 Ultra 上的主线程自旋、事件读取、同步验证与四元组辅助函数调用（2026-10-19）

English: [2026-10-19-spin-events-quad.md](2026-10-19-spin-events-quad.md)

10-19 09:40–11:30（新西兰夏令时）在 Redmi K50 Ultra（Adreno 730、Vulkan 1.1、Android 15）上测，游戏加速开着。构建为 `android/linux-build`，3D 比例固定 0.75，另有注明的除外。

## 宿主开关的按时间对照

引擎的进程内对照（`gfx-ab-toggle`）只管得到引擎里的开关。逐帧 TSV（`DM_NVN_TSV`）现在多了 `@mono_s`，即该帧的单调时钟绝对秒数。凡是按同一相位（单调秒数 / N 为偶数 = 开）切换的开关，都能在事后逐帧分组，再按相邻的开、关时段求差。先后分开跑两次，比不出长帧率：没开自旋的两次营地，超过 18 ms 的帧一次 9.3%、一次 5.3%，差得和下面的效果一样大。

## 客体主线程短等待先自旋再睡（PR #26）

D2R 主线程每帧约 45 次等两个工作线程持有的客体锁，其中 81% 只等 10–25 µs。`DM_HLE_SPIN_US=30`（安卓缺省）时，主线程睡前先轮询自己的唤醒标志至多 30 µs。用 `DM_HLE_SPIN_AB=10` 在一次营地运行里每 10 s 切换一次（22 个时段，每组约 6,100 个稳定帧）：

| | 自旋 | 不自旋 | 开 − 关，21 对相邻时段（95% 置信区间） |
|---|---|---|---|
| 超过 18 ms 的帧 | 6.94% | 11.78% | −4.87 ± 0.97 个百分点 |
| 超过 20 ms 的帧 | 0.34% | 0.82% | |
| 帧时间 p99 | 19.08 ms | 19.76 ms | |
| 每帧进程 CPU | 21.67 ms | 22.22 ms | −0.51 ± 0.13 ms |

11 个自旋时段的长帧都少于 11 个不自旋时段中的任何一个。开着自旋，整个进程的 CPU 反而更少。

## 没有直接读待发布的事件字（#9）

帧重叠（`gfx-defer-events` = 2）在槽退休时才写 SignalEvent 的值。维护者问：这期间客体或宿主会不会直接读那块内存。

诊断标记 `gfx-event-guard` 把每个待发布事件字所在的页设成 `PROT_NONE`，值落地才放开；缺页连同调用方一起计数。引擎自己拷客体内存时，在拷贝前后放开这一页，单独计数。运行时关掉 vcache、tex-dirty 和 wtrack。

| 场景 | 设防的事件 | 落在待发布字上的缺页 | 同页别处的缺页 | 引擎拷贝 |
|---|---|---|---|---|
| 营地，110 s | 6,419 | 0 | 0 | 32,097 |
| 开机、传送进罪恶洞穴、定种子打斗，108 s | 6,479 | 0 | 0 | 32,397 |

碰到这些页的只有引擎自己：

- `stream_buffer` 拷页内偏移 0 起的 64 字节（那个字在 +0x54）；
- `write_report` 在 +0x60 写计数器报告（旁边的字在 +0x108）。

`nvnEventGetValue` 读之前先发布待发布的事件，而且从没碰上过待发布的事件（`cpu_reads_pending=0`）。CPU 的 `nvnEventSignal` 是直接写入，没有一次写操作缺页。

## 同步验证下的呈现重叠（#9，PR #28）

Khronos 验证层（1.4.363.0 安卓二进制）只对本 App 作为 GPU 调试层加载，开 `validate_sync`、关 `validate_core`，呈现重叠和帧重叠都开着。

它只报了一种隐患：呈现端对每张取到的交换链图像换布局时，源阶段写的是 `TOP_OF_PIPE`，而提交在 `TRANSFER` 阶段等获取信号量（`SYNC-HAZARD-WRITE-AFTER-READ`）。这与重叠无关，`main` 里也是同一个屏障。源阶段改为 `TRANSFER`（PR #28）后，营地（约 100 s）和传送加定种子打斗（约 110 s）一条消息也没有。所以两次 blit 在途时游戏输出图上没有隐患，帧重叠时引擎的资源上也没有。

## 经翻译器辅助函数的四元组 shuffle（PR #27）

`main` 带守卫的四元组改写，在 182 个带 shuffle 的片元模块里一个也没改。翻译器把每条 SHFL 都放进一个直线辅助函数（Ryujinx 的 `ShuffleXor`），而守卫只接受主函数里的 shuffle。278 处片元调用都传异或 1（86 处）或 2（192 处）与 SHFL 掩码 `0x1c03`，所在的条件要么按绘制统一，要么在 alpha 测试的 kill 之后。

**这些辅助函数还有第二个错。** 它们的 clamp 检查按 32 道线程束写：`(lane ^ x) <= ((lane & 0x1c) | 3)`。真机报告片元着色器的子组是 64 道（`subgroup size=64 stages=0x30`），32–63 号 lane 检查不过，每次四元组交换都拿回自己的值。这是每个波前的一半，与辅助调用无关。

PR #27 在调用处把这种调用改成由精细导数求邻居，前提是三条都成立：

1. 对 32 条 lane 逐条执行辅助函数，证明它是四元组交换；
2. 调用处于动态统一控制流：只有 kill 的分支不算分叉，kill 之后再读其谓词，对存活调用统一；
3. 位从产生到使用都承载浮点数，途经 Ryujinx 的寄存器变量和 bitcast。

改写覆盖 278 处里的 271 处，其余 7 处搬运的是整数。

调用整个换掉。若保留原调用作为非有限值的回退，黑方块会回来，GPU 也多花约 3 ms。定种子的罪恶洞穴打斗，比例 0.75：

| 改写 | GPU ms | 绘制数 | fps | 黑方块 |
|---|---|---|---|---|
| `linux-build` 自己的（在辅助函数里换成导数） | 14.62–14.67 | 1,027 | 60 | 无 |
| 调用处改写，原调用留作回退 | 18.24–18.30 | 1,081 | 54 | 有 |
| 调用处改写，整个换掉（PR #27） | 15.09–15.27 | 1,077 | 60 | 无 |

## 试过、没有可测收益：描述符记忆命中只在变化后才重查图像

描述符记忆每次命中都要把缓存的每张图像的注册记录重查一遍。改成用一个代号计数，没有注册或图像变化时就跳过这些检查（分支 `android/desc-hit-gen`，对照目标 `hitgen`）。营地里 16 对时段，渲染线程提交 CPU 变化 −0.066 ± 0.086 ms，测不出来。先不提交，因为漏掉一次代号递增就会用到过期的描述符。
