# Redmi K50 Ultra 上的 GPU 剖析，以及 120 Hz（2026-10-18）

English: [2026-10-18-gpu-profile.md](2026-10-18-gpu-profile.md)

17:40–18:40（新西兰夏令时）在 Redmi K50 Ultra（Adreno 730、Vulkan 1.1、Android 15）上测。构建为 `android/linux-build`，用安卓缺省，营地；未注明时 3D 比例固定 0.6。诊断在分支 `android/pipe-stats` 上，不合并。120 Hz 的改动是 PR #17（分支 `android/frame-rate`）。

## 这台手机上能用哪些 GPU 剖析器

- **Perfetto**：这台手机上 GPU 相关的数据源只有 `android.gpu.memory`，没有 `gpu.counters`，也没有 `gpu.renderstages`。所以 Android GPU Inspector 的系统剖析拿不到 GPU 计数器和渲染阶段。
- **KGSL 性能计数器**（AGI 和 Snapdragon Profiler 读的就是它）：探针分别以 shell 和 App 身份（`run-as`）运行，都能打开 `/dev/kgsl-3d0`、列出计数器组（SP 24 个、UCHE 12 个、TP 12 个、RB 8 个、LRZ 4 个等）并预留计数器。但每次读都返回 `EPERM`：在这台未 root 的手机上，内核不让 App 和 shell 读它们。
- **Vulkan**：没有 `VK_KHR_performance_query`。驱动提供 `VK_KHR_pipeline_executable_properties`，即每条管线的编译统计。下面用的就是它。

## 驱动对着色器的统计

`gfx-pipe-stats`（配合 `gfx-no-warm`，让每条管线都按需建）记下每条管线的统计，以及每条管线每帧的绘制数。

| 片元着色器（3D 主通道） | 每帧绘制数 | 指令（其中 ALU） | 寄存器 | 最多同时活跃调用 |
|---|---|---|---|---|
| `5c1ca4e7c3e4657c` | 284 | 3,710（1,800） | 22 | 1 |
| `38f344adf801b153` | 119 | 3,938（1,959） | 25 | 1 |
| `358197ac3db59cbc` | 72 | 3,393（1,685） | 22 | 1 |
| `acd655d88042767c` | 18 | 4,163（2,135） | 25 | 1 |
| 简单着色器（界面、深度、阴影） | | 1–400 | 0–5 | 3 |

- 这几个重的光照着色器跑在驱动报告的最低占用率上（1，简单着色器是 3），所以几乎掩不住纹理延迟。
- 没有着色器用 16 位 ALU。只有一个计算着色器用暂存内存。
- 最重的顶点着色器 545–983 条指令，阴影通道的是 910 条。
- 主通道的着色器都不丢弃像素，所以深度预通道之后提前深度剔除照常起作用。

## 试过、没有收益的

- **对最重的五个着色器跑 `spirv-opt -O`**（经诊断用的 `files/dm/spv-override/<key>.spv` 载入）：翻译器把每个 Maxwell 寄存器存成一个独立变量（每个着色器约 2,800 个变量、5,000 次读、3,000 次写），`spirv-opt` 几乎全部消掉（剩 37 个变量，体积减到三分之一）。驱动的产出不变：寄存器和活跃调用数相同，指令数差不到 1%，主通道 6.71–6.79 ms，原来 6.78 ms。Adreno 编译器本来就做了这些。
- 翻译出来的着色器里没有半精度模拟，也没有函数内数组。
- **128 宽的片元波**（`VK_EXT_subgroup_size_control`）：驱动只允许计算着色器指定子组大小（64 或 128）（`requiredSubgroupSizeStages` = 计算）。
- **不开 `robustBufferAccess`**（诊断 `gfx-no-robust`）：编译出的代码相同，108 个着色器共 89,662 条指令，开着是 89,663 条，寄存器也一样。越界检查在这里不要钱，引擎照旧依赖它。
- **临时命令池**（`VK_COMMAND_POOL_CREATE_TRANSIENT_BIT`）：重置一个槽的池仍是每帧 404–415 µs，结束命令缓冲 268–290 µs，与不加标志一样。
- **缓冲到贴图的拷贝**只在载入时发生（起初每帧 136 次，营地里没有），跳过重复拷贝对游玩没有帮助。

## 120 Hz

屏幕支持 60、90、120 Hz，系统设置是 120（`user_refresh_rate=120`；桌面跑 120 Hz）。但游戏运行时显示降到 60 Hz：游戏的表面没有投刷新率票，安卓就选够用的最低档。

呈现端现在给游戏表面投 120 Hz 的票（`ANativeWindow_setFrameRate`，运行时从 `libnativewindow` 取），游戏里显示就保持在 120 Hz。游戏仍按 60 帧出图（`nvn_pace_hz` 取刷新率的整数分之一里不低于 60 的最大一档）。区别在赶不上 16.7 ms 的那一帧：现在在屏上停 25 ms，而不是 33.3 ms。

营地、比例固定 0.75、同一个构建，两次都是 47.9 fps，SurfaceFlinger timestats（相邻两次上屏的间隔）：

| 显示 | 在屏 16.7 ms 的帧 | 25 ms | 33.3 ms | 50 ms |
|---|---|---|---|---|
| 不投票：60 Hz | 71% | — | 28% | 少数 |
| 投 120 Hz | 39% | 61% | 0 | 0 |

同样的帧率，现在没有哪一帧会在屏上停满两个 60 Hz 周期：跳变是 1.5 倍而不是 2 倍，最长停留从 33–50 ms 降到 25 ms。两次都没有丢帧。

标记 `gfx-frame-rate` = N（Hz）改投票值；0 = 不投票。

## 按游戏输出尺寸出图（PR #18）

呈现端原来的交换链是 2712×1220：每帧先清整幅，再把游戏 2000×900 的输出用最近邻放大上去；随后显示引擎把这一层转进竖屏（`DEVICE` 合成、`ROT_90`，从没走 GPU 合成）。现在窗口缓冲取游戏输出的尺寸（`ANativeWindow_setBuffersGeometry`），呈现端 1:1 拷贝、不再清屏，由显示引擎在旋转的同时放大。

| | 交换链 | 呈现端每帧 GPU |
|---|---|---|
| 之前 | 2712×1220 | 230 µs |
| 之后 | 2000×900 | 163 µs |

每帧少约 13 MB 内存流量，放大比最近邻平滑，其余画面不变。标记 `gfx-present-native` = 0 保留原来的交换链；`gfx-present-timing` 记下呈现端的 GPU 时间。

## 触摸层每个刷新周期都重画（PR #19）

打斗时最忙的线程是游戏线程（X2 核的 72%）、两个游戏工作线程（各 15–20%），以及安卓自己的 `RenderThread`，占 12%。在游戏上面画触摸按钮的 `TouchOverlay` 每次 `onDraw` 末尾都再请求一次重画，所以 HWUI 每个刷新周期都画它：120 Hz 下 10 秒画了 1,228 帧。现在每个刷新周期只查一次原生布局，变了才重画。

| 邪恶洞穴 | 10 秒内 HWUI 帧数 | `RenderThread` CPU | 游戏每帧 GPU |
|---|---|---|---|
| 之前 | 1,228 | 一个核的 12.2% | 14.55 ms |
| 之后 | 0（没按任何键） | 不在忙线程之列 | 14.43 ms |

按下的键照样高亮，松开就恢复。

## 异步翻译仍然更慢

`DM_NVN_SYNC=0`（翻译在自己的线程上，即 iOS 的方式）时，固定种子的洞穴打斗只有 35.2 fps，同步模式是 59.6：游戏每帧花 13–15 ms 等栅栏，等的是翻译线程还没提交的工作；一半的帧掉了，动态比例一路降到 0.6。安卓缺省仍是同步模式。

## MIUI 游戏加速：最大的一步

App 不在 MIUI 的游戏加速列表里（安全中心 → 游戏加速 / 游戏空间 → +）时，MIUI 会压着它的 CPU 和 GPU 频率；清单里的 `appCategory="game"` 不够。把 D2R Mobile 加进去后，游戏运行时 `settings get secure gb_boosting` 为 1，上限放开：

| 营地 | 不在游戏加速里 | 在游戏加速里 |
|---|---|---|
| X2 核上限 | 2.25 GHz | 3.19 GHz（实际跑在这个频率） |
| A710 核上限 | 2.57 GHz | 2.75 GHz |
| 比例固定 0.6 | 53 fps，GPU 17.7 ms，CPU 11.6 ms | **60.0 fps**（出图节奏的上限），GPU 13.8 ms，CPU 10.6 ms |
| 产品缺省（动态比例） | 停在 0.65，50–51 fps | **一直保持 0.75**，58–60 fps，GPU 15.6 ms；帧间隔中位数 16.6 ms |

GPU 快了约 28%，可见它的频率也被压着。代价是发热：电池约 4 分钟从 32.4 °C 升到 38.0 °C，X2 的上限已降到 3.00 GHz。MIUI 上的玩家应把游戏加进游戏加速；长时间游玩会更热，频率降下来时动态比例会降分辨率。

## 顺带发现的一个正确性问题

四个计算着色器（`098a126f92bf533a`、`7c16e695919ffc6e`、`fc85981c8d9148c9`，工作组 8×8；`fbc4a0eb955f5960`，128×1）用线程束聚合追加来建每个图块的列表：最高的活跃通道用一次原子加预留 `bitCount(ballot)` 个位置，每个通道写在 `base + bitCount(ballot & 比它低的通道)`。

翻译只取 `subgroupBallot(...).x`，即 Maxwell 一个线程束的 32 个通道。Adreno 的子组是 64 宽，所以第 32–63 号通道不在计数里，而且算出的都是同一个越过预留范围的偏移：它们的条目互相覆盖。修法是一个 SPIR-V 改写，在 64 宽的子组里模拟 32 宽的线程束（虚拟通道 `id & 31`，选票取第 `id >> 5` 个字，洗牌限制在各自的半边里）。已在 PR #21 里做了，代价见 [2026-10-19-review-fixes.zh-CN.md](2026-10-19-review-fixes.zh-CN.md)。
