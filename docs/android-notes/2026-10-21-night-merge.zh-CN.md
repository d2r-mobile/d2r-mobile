## 每帧拷贝

营地每帧要 18.67 MB 的存储快照，却没有一份整份拷贝：写跟踪只拷大只读缓冲里的脏页（每帧 26.5 KB）。每帧整份拷贝的是：uniform
2.08 MB、texel 1.00 MB、顶点 0.06 MB、索引 0.01 MB（`snap_mb_per_frame`，`e27cbab` 起分开整份拷贝和请求量）。

每 10 s 截一次图（每次卡约 20 帧），R1 全程比例停在 0.85。`e267a6b` 之前，同样的脚本会把它降到 0.60（2026-10-20 的 T4）：现在

- 半透明 draw 的后台建管线（`fc46144`）从没生效：D2R 每帧重置 21 次样本计数，从第一次重置起每个 draw 都计样本，却从不记录

  （p1 28.7 对 28.8 fps）：最慢的帧是不透明管线，它们仍在帧里编。开关保持关闭。
- 热缓存下切换区域要 3-4 帧 25-38 ms（R4，进奶牛关）；冷缓存下其后有 238 ms 和 312 ms 的单帧。
- 驱动管线缓存原来在有新管线时每 300 帧由图形线程写一次：整份（这里 17.7 MB），每次热启动六次，因为预热的 392 条虽然驱动已有，

## 没人读的遮挡查询值得留着

饱和测试台上（营地，固定比例 1.0，进程内每 10 s 切换，目标 `occ`），关掉每帧约 47 个遮挡查询反而让 GPU 更慢：每帧 18.78 对
17.09 ms（开 − 关 −1.75 ± 0.24 ms，20 对），52.6 对 57.1 fps。D2R 从不读这些结果。猜测是查询活动时 Adreno 驱动换了一种画通道的
方式，没有再追。若改为出现样本报告之后才开始查询，就会白丢这 1.75 ms。开始查询时不带 `VK_QUERY_CONTROL_PRECISE_BIT`（Q1，同一测试台）
没有区别：GPU +0.01 ± 0.06 ms，CPU −0.05 ± 0.12 ms。

## 跨槽的待写视图（`17c2894`）

待写视图（快照或拷贝源落在尚未写回的 GPU 结果上）指向产生它的槽的回读区。产生方退休、重新录制时，另一个槽若仍在 GPU 上并持有这种
视图，新录制的 CPU 拷贝就写进那些读取正在用的内存；开着 `gfx-wb-skip` 时，拷进去的可能是更旧的客体内存，因为被取代的写回从没落地。
`NVN PERF xview` 记这件事：营地、Den of Evil、奶牛关都是每帧 6 个视图、1 次这样的重用（视图大小 16 KB、64 KB 和两个 5 KB）。main
出于同样的生命周期问题拦下了待写视图的链。

`gfx-xview-arena`（`cf72c52`，关；A/B 目标 `xarena`，`91d6956`）在这种情况下改录到第二个回读区，视图的内存就保住了，不加等待。
它如预期每帧切换一次，GPU 时间相同，但进程内对比（XA，营地，20 对）每帧多花 1.72 ± 0.21 ms CPU：描述符 memo 的键含缓冲句柄，各槽
的回读缓冲来回交替后，每帧约 145 个 set 要重建（memo 未命中 145 对 0，set 缓存未命中 155 对 10）。所以保持关闭；修法必须让各槽的缓冲
保持不变。它仍可当开关，用来检验这个竞争是不是 OnePlus 13 上一帧黑色光照块（2026-10-20）的原因；这一点没有证实。

## 合并 main（`4f859cb`，PR #27 为 `6213e2c`，之后 `c2f9fa4`、`2594e7a`、`50af02c`）

main（`d187015`）带来维护者改写过的 PR #3、#9-#10、#12-#16、#19-#21 与 #23，调试环境、池标志登记表、`Download/S2X/D2R Mobile/data`
路径和 iOS 改动。两边都改过的引擎代码保留本分支后来的安卓版本，main 的修正适用处一并带入：

- 保留：上一 draw 的管线 memo（它的着色器、布局和 pass 只在关闭时释放，且在清 memo 的 `clear_*` 之后）、内联的 `get_image` 快路径
  （PR #30）、遮挡计数段（现用 main 的辅助函数名，main 的 `occlusion_batch_test` 可以直接测它）和贴图脏页检查。
- 取自 main：防溢出的写回范围与覆盖判定、`copy_texture_buffer`（在取得任何图像引用前完成 CPU 读；BC 拷贝走行/层间距规划）、ASTC
  到解码 BC 的 blit 规划、驻留 texel 的上限、quad/warp 包装（按着色器计数；warp 改写后重查能力）和写跟踪的范围保护。
- main 的逐操作读预检（`beebb5b`）放在 `gfx-read-preflight` / `DM_GFX_READ_PREFLIGHT` 后面，缺省开，与 main 相同。安卓 App 把它关掉：
  延后事件下总有约 8 个报告待写，开着就几乎每个 draw 前同步一次 GPU；营地与 Den of Evil 的记录里 CPU 访问从没碰到待写结果

- 驻留 texel 路径只要与待写回有重叠就回退，不只是完全覆盖时：没有预检时，建 set 的时候可能有只覆盖一部分的待写回。
- 呈现端缺省保留 120 Hz 投票（main 每次初始化重置为 0）。
- `Download/S2X/D2R Mobile/data` 不存在时 App 沿用 `Download/data`。第一版合并按 `Download/data` 里有没有 `.build.config` 判断，在
  Redmi 上启动即停：它的资源目录里没有这个文件（由覆盖层提供）。

  合并后的构建需要重新生成的覆盖层。

## 上午：三个待查方向（09:00-11:10）

### 遮挡查询那 1.75 ms 从哪里来

饱和测试台上的分通道计时（营地，固定比例 1.0，每 600 帧计一帧；P1 有查询，P2 用标记 `gfx-no-occlusion`）把它落在主 3D 通道：有查询
每帧 6.46 ms，没有 7.70 ms。一个 34 次 draw 的三目标通道 0.66 对 1.00 ms。深度预通道和主通道的 draw 与顶点相同，却没有变（1.21 对
1.19 ms），阴影图和计算派发也没变。HUD 通道（744 次四顶点 draw）有查询 0.82 ms、没有 0.52 ms，但只让四顶点 draw 不开查询（A/B 目标
`occquad`，E5）没有任何变化（GPU −0.07 ± 0.12 ms），可见那个差别跟着别处的查询。没有找到值得改的查询布置。

### 两个槽回读区之间的竞争，已经关上

把产生方的缓冲挪开的两种做法都费 CPU：第二个回读区每帧 1.72 ± 0.21 ms，同一块的另一半 1.85 ± 0.22 ms。每帧约 145 个 memo 过的
描述符 set 在固定的缓冲和偏移上绑定只读存储，它们每帧都未命中。

`gfx-xview-guard`（`f03bdf7`）让缓冲留在原处。新回读缓冲若与读取方看过的范围重叠，就不由 CPU 写：内容先进流缓冲，再由排在该槽自己
命令缓冲之前提交的序言命令缓冲在屏障之后拷进去，屏障保证读取方的工作先完成。进程内对比（XG，营地，20 对）每帧由 GPU 写 6 个缓冲、
1.37 MB，测不出代价：CPU −0.15 ± 0.21 ms，GPU −0.17 ± 0.15 ms。安卓 App 缺省开启（`4529e08`），取代 `gfx-xview-arena`。它是否改变
OnePlus 13 上一帧的黑色光照块，还要在那台手机上看。
