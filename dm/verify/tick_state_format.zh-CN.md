# 逐拍游戏状态哈希格式

English: [tick_state_format.md](tick_state_format.md)

游戏的服务端逻辑按「拍」推进（每拍处理一次全部单位）。每一拍开始前，把游戏里全部单位的关键字段算成几个哈希、记一行；两边逐拍相同，就说明游戏逻辑走得一模一样。两边指**真值**（用打了补丁的 Ryujinx 模拟器跑原版游戏得到的参照数据）与**宿主**（`dm/host` 的 `dmhost`）。两边跑的是同一份 Switch 版 3.3.94012 程序，逐字节比。

- 真值侧：`dm/verify/oracle/swtick.py` 经模拟器的 GDB 接口读，录一局时写成 `<局目录>/ticks.jsonl`。录制用的模拟器驱动脚本不随仓库提供，所以依赖真值的检查在仓库外跑不了。
- 宿主侧：环境变量 `DM_TICKS=<路径>` 打开；`DM_TICKS_N=<拍数>` 记满即正常退出；`DM_TICKS_FULL=1` 另出逐单位明细。
- 对拍：两份 `ticks.jsonl` 按拍号对齐，报每一格首个不同的拍号；共同拍数 < 10 不下结论。对拍脚本 `selfcmp.py` 属于模拟器驱动脚本那一组，不随仓库提供。

## 采集点与基址

- **采集点**：服务端拍入口 `main + 0x5d3bc0`，在入口第一条指令执行之前取（拍号尚未自增）。
- **基址 G** = 入口处的 `x0`。G 是游戏对象，嵌在游戏哈希表节点里：G = 节点 + 0x10（节点 = 槽数组 `main + 0x2d665d8` 的 ID 查哈希表 `*(main + 0x2d685e0)` 所得）。
  **本文所有偏移都以 G 为基址**：建局函数 `0x5d0bd0` 以节点为基址写的 `+0x1b8`，就是这里的 `G + 0x1a8`。
- **拍号** = `u32 [G+0x170]`（入口处读，等于本拍开始前的值）。
- 同一拍号只取一次（模拟器会重复报告同一次断点命中，按拍号去重）；拍号必须逐一连续，断档报红。

## 每拍一行 JSON

```
{"tick":39,"n":[4,12,24,0,21],"h":["…16 位小写十六进制…" ×6],"bad":0}
```

- `n`：5 类单位的个数（0 玩家 / 1 怪 / 2 物件 / 3 飞弹 / 4 物品）。
- `h`：6 格哈希（5 类单位 + 全局种子）。
- `bad`：读不到的单位指针数 + 自报类型与所在表不符的单位数。
- 其他字段（game、dt、reads）只供人看，不参与对拍。

## 单位表与字段

偏移全部相对各自结构的起点。

| 类 t | 表 | 说明 |
|---|---|---|
| 0 玩家 | G+0x2230 | 每表 128 个桶（u64 指针），桶内单链 `next = [u + 0x158]`，每链最多 4096 |
| 1 怪 | G+0x2630 | |
| 2 物件 | G+0x2a30 | |
| 3 飞弹 | G+0x3230 | 注意 3、4 的表序与地址不单调 |
| 4 物品 | G+0x2e30 | |

单位 u 的字段：

| 字段 | 读法 |
|---|---|
| type, cls, id, mode | u32 [u+0x0], [u+0x4], [u+0x8], [u+0xC] |
| act | u8 [u+0x18] |
| rlo, rhi（单位种子） | u32 [u+0x28], [u+0x2C] |
| 坐标（仅 t = 0/1/3） | path = u64 [u+0x38]；u16 xf=[path+0], x=[path+2], yf=[path+4], y=[path+6]；path 为 0 或读不到时四项都取 0；其余类四项恒 0 |
| statlist（t = 0/1/4） | sl = u64 [u+0x88]；arr = u64 [sl+0x30]，cnt = u32 [sl+0x38]；取 min(cnt, 96) 项，每项 8 字节原样（u32 a = 层<<16 \| statId，u32 b = 值） |
| 物品附加（仅 t = 4） | d = u64 [u+0x10]；iq=[d+0x0]，is_lo=[d+0x4]，is_hi=[d+0x8]，iflags=[d+0x18]，iinit=[d+0x10]（u32）；d 为 0 时五项取 0 |

## 哈希

FNV-1a 64，偏移基 `0xcbf29ce484222325`，乘数 `0x100000001b3`，逐字节，数值一律小端 u32。

1. 每类 t 的哈希从偏移基起；全部单位按 (type, id) 升序后依次并入其 type 对应的格（type ≥ 5 的不计）。
2. 每个单位依次并入：
   - 9 个 u32：type, cls, id, mode, act, x, y, xf, yf
   - 2 个 u32：rlo, rhi
   - 仅 t = 4：5 个 u32：iq, is_lo, is_hi, iflags, iinit
   - 仅 t = 0/1/4：u32 项数，再逐项 8 字节原样
3. 第 6 格（全局种子）= 偏移基并入 8 字节 `[G+0x1a8]`（u32 lo + u32 hi 原样）。
4. 输出为 16 位小写十六进制字符串。

## 确定性（对拍的前提）

两边要逐拍相同，输入必须相同：

- **建局种子**：建局函数 `0x5d0bd0` 读 `u32 [main + 0x20a0074]`；≠ `0xffffffff` 时种子 = {该值, 666}，否则取系统时钟。两边须在建局前写同一个值：真值侧是驱动脚本的 `--game-seed N`，宿主 `DM_GAME_SEED=N`。
- **建局时刻**：建局时读一次系统时间。真值侧是驱动脚本的 `--fix-time <秒>`，宿主 `DM_FIXED_TIME=<秒>`，给同一个值。
- **存档**：两边各用同一份标准存档（`$DM_ROOT/data/switch/save_ref_warlock`）的新副本开局；存档内容指纹用 `dm/verify/savesha.sh` 算，跑前记下。
- **输入**：客户端发给服务端的输入一律以真值录下的命令包序列为准（见 [command_packet_format.zh-CN.md](command_packet_format.zh-CN.md)）。命令包与**系统类消息**（`0x6d` 心跳、`0x6f` 进度等）都要按原拍号注入原字节，宿主自己产生的同类消息丢弃（进局时的 `0x67` 加入照常放行）。系统类消息到达的拍号取决于客户端快慢，其中 `0x6f` 决定服务端何时插入同步，属于与时序相关的输入；不注入的话逐拍状态对不上。
