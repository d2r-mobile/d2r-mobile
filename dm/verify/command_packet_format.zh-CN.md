# 客户端命令包序列格式

English: [command_packet_format.md](command_packet_format.md)

游戏内部分客户端与服务端两半：玩家的操作由客户端变成「命令包」交给服务端处理。把一局里的命令包按先后录成文件，有两个用处：在**宿主**（`dm/host` 的 `dmhost`）上原样回放，让服务端走出与**真值**（用打了补丁的 Ryujinx 模拟器跑原版游戏得到的参照数据）相同的一局；或者比较两边在同样按键下发出的命令包是否相同。真值录制与宿主回放共用本格式。

## 采集点

- 客户端命令分派函数 `main + 0x6e5b40(G, 单位, 包, 长度)`。入口处：
  `x0` = G（游戏对象，与 [tick_state_format.zh-CN.md](tick_state_format.zh-CN.md) 同一基址），`x1` = 发包的单位（可为 0），`x2` → 包字节（包号 = 首字节，须 < 0x67），`w3` = 长度。
- 处理函数表 `main + 0x20a4190`（0x67 项，空项即非法包号）。
- **系统类消息**走另一条路：`main + 0x6310b0(buf, 包长)`（跳转表 `0x1daf73c`），buf = u32 客户端号 + 包。收包泵 `0x5d3960` 每拍先抽干系统类队列，再处理命令包。

  | 包号 | 长 | 含义 | 回放处理 |
  |---|---|---|---|
  | 0x67 | | 加入 | 进局时照常放行（用宿主自己的） |
  | 0x6c | | 角色数据分块 | 按文件注入 |
  | 0x6d | 13 | 心跳：比较客户端结构 +0x6c4 与 +0x6c0，不同就回同步消息并更新 | 按文件注入 |
  | 0x6f | 5 | 进度：客户端上报的进度值写进客户端结构 +0x6c0（如传送后「新区域加载完成」） | 按文件注入 |
  | 0x6a / 0x6b / 0x6e | | 默认丢弃 | — |

## 每条一行 JSON（按调用先后）

```
{"tick":57,"unit":1,"len":5,"pkt":"0300120034"}
```

| 字段 | 含义 |
|---|---|
| tick | 调用时 `u32 [G+0x170]`（服务端当前拍号） |
| unit | `u32 [x1+0x8]`（单位 id；x1 = 0 时为 null） |
| len | `w3` |
| pkt | 包字节前 min(len, 512) 字节的小写十六进制 |
| q | 仅系统类消息有，值 `"sys"`；此时 unit 恒 null，tick 取当前拍号（最近一次拍入口的 `[G+0x170]`），len = 包长，pkt **不含**开头 4 字节客户端号 |

系统类条目例：`{"tick":201,"q":"sys","unit":null,"len":5,"pkt":"6f…"}`。

宿主侧用 `DM_C2S_LOG=<路径>` 录，逐字段同格式。

## 两层判据

1. **服务端层**：宿主不吃手柄，在拍号 = tick 的那一拍、按文件顺序把每条包原样交给 `0x6e5b40`（`DM_C2S_REPLAY=<文件>`，同时关闭客户端自发的命令；只用于测试），要求逐拍 6 格状态与真值一致。
   - **系统类消息必须由真值录、宿主按拍注入**。`0x6f` 到达的拍号与值决定服务端在哪一拍插入同步消息（服务端几百处发消息前都比较 +0x6c4 / +0x6c0 并补发），这取决于客户端快慢，两边天然不同，属于与时序相关的输入。
   - 回放时宿主自己的系统类消息从文件首拍起一律丢弃（进局前的 `0x67` 加入照常放行），改为在原拍号注入真值录下的原字节；同一拍内先注入系统类、再分派命令包，与收包泵的顺序一致。
   - 过了文件末拍，宿主客户端自发的消息重新放行。
2. **客户端层**：同一份按键脚本下，两边产生的命令包序列**只比内容与顺序**（忽略 tick），外加 UI 消息流一致（[ui_message_stream.zh-CN.md](ui_message_stream.zh-CN.md)）。

对比工具：`dm/verify/c2scmp.py <A c2s.jsonl> <B c2s.jsonl> [--ids]`。它报两件事：内容与顺序是否一致（客户端层判据）、同序号的包落在的拍号是否相同。`--ids` 只比包号序列并折叠连续相同的包号，给摇杆这类连续动作用。退出码：0 = 内容与落拍都一致，1 = 内容一致但落拍不同，2 = 内容不一致，3 = 任一侧 0 条。

## 真值侧录制

真值侧的录制由模拟器驱动脚本完成。这些脚本不随仓库提供，所以依赖真值的检查在仓库外跑不了。录一局，局目录下得到 `c2s.jsonl`（本格式）与 `ticks.jsonl`（拍状态格式）。驱动一局有两种写法：

- **动作表**：每行「进局后第几拍 `<TAB>` 输入指令」。
- **计划**（与动作表二选一）：按游戏数据推进。走向物件或怪时，用玩家与目标的坐标闭环推摇杆；每次按键都以 UI 消息、命令包、飞弹数或换场景来确认。
- 服务端层六格覆盖用的那份计划里，选技能的包 `0x3c` 在真值侧就地改写了技能号，录下的 `c2s.jsonl` 是改后的字节——这样的文件只用于服务端层回放，客户端层判据不能用带这种改写的计划。

## 经 GDB 录制时要注意的两点

真值侧靠模拟器的 GDB 接口在上面两个函数入口下断点来录。两条规矩都实现在 `oracle/swgdb.py` 里（`wait_stop` 自动切线程、`_stash` 去重、`step_over` 等本线程走过断点）：

- 模拟器每收到一次断点，就把「寄存器读的是哪个线程」设成最新撞断点的那个线程。处理先到的停止包之前必须先切回该包的线程，否则读到别的线程的 PC，会把这次命中当成无关的停止放过，造成漏拍。
- 停在断点上、尚未处理的线程，每次全体继续都会在同一断点再停一次。暂存的停止包要按线程去重，否则同一个命令包会记两次。
